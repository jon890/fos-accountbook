# ADR-F42: services 가 받는 백엔드 응답도 Zod 로 검증한다 (2026-10-02)

- **status**: `accepted`
- **결정**: `src/services/**` 가 `serverApiGet` 같은 API 래퍼로 받는 백엔드 응답의 `data` 를 Zod 스키마로 검증한다(ADR-F06 의 입력 검증을 응답까지 넓힌다).
  래퍼는 선택 인자 `schema` 를 받아 `response.data` 를 `schema.parse` 한다. 스키마는 `src/lib/schemas/responses/` 에 도메인별로 두고, 화면이 쓰는 타입은 가능한 곳에서 `z.infer` 로 만든다.
  스키마는 알 수 없는 필드를 버리고 통과시킨다(`z.object` 기본 동작). 빠진 필드와 타입이 다른 필드는 `ResponseValidationError` 로 던진다. 오류 로그에는 엔드포인트와 Zod 이슈 경로만 남기고 응답 값은 남기지 않는다.
  실패를 빈 값으로 대체하던 곳(분석, 대시보드)은 대체를 유지하되 검증 오류를 반드시 로그에 남긴다.
  `void` 를 돌려주는 쓰기 호출은 검증하지 않는다.
- **맥락**: 응답은 타입 단언(`response.json<T>()`)만 거쳐, 백엔드가 필드를 바꾸면 화면이 조용히 빈 값이나 `undefined` 를 그렸다(#209). 실제로 지출 목록 응답에는 `category` 가 없는데 분석 TOP 5 가 그 필드를 읽어 늘 「기타」 로 보였다(fe-plan12 에서 발견).
  카테고리 종류 분리처럼 백엔드와 프론트를 함께 바꾸는 변경이 잦아졌다.
- **대안 기각**:
  - 서비스마다 `safeParse` 를 직접 부르기: 21곳이 각자 오류 처리와 로그를 만들고, 빠뜨려도 막을 수 없다.
  - `.strict()` 로 모르는 필드도 실패: 백엔드가 필드를 더하기만 해도 화면이 깨진다.
  - OpenAPI 에서 타입 생성: 생성 도구와 백엔드 springdoc 계약 정비가 먼저 필요해 범위가 크다.
- **결과**:
  - 얻는 것: 응답 계약이 어긋나면 그 엔드포인트 이름과 필드 경로로 바로 드러난다. 같은 모양의 타입 사본이 줄어든다.
  - 감당할 것: 백엔드 응답 필드를 바꾸면 스키마도 함께 바꿔야 한다. 큰 목록(최대 3000건) 검증 비용이 응답마다 든다.
- **적용 범위**: `src/lib/server/api/`, `src/lib/schemas/responses/`, `src/services/**`, `src/lib/errors/action-error.ts`.
