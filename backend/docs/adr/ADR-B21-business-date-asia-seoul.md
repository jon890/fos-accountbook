# ADR-B21: 업무 날짜 판정은 Asia/Seoul로 하고 기본 Clock은 유지한다 (2026-10-01)

- **status**: `accepted`
- **결정**: 「오늘」 과 「이번 달」 같은 업무 날짜 판정과 스케줄러 cron 은 Asia/Seoul 로 한다. 기본 `Clock` 빈은 JVM 기본 시간대를 유지하고, 업무 날짜를 계산할 때만 공통 업무 시간대 상수로 `clock.withZone(...)`을 적용한다.
  JVM 기본 시간대와 저장된 `LocalDateTime` 값의 해석은 바꾸지 않는다.
- **맥락**: 백엔드 이미지에 시간대 지정이 없어 JVM 은 UTC 로 돈다. `ClockConfig` 가 `Clock.systemDefaultZone()` 이라 스케줄러만 Clock 을 쓰는데 그것도 UTC 였고, 나머지는 `LocalDate.now()` 를 직접 불렀다.
  그래서 KST 0~9시에는 「이번 달」 기본값, 반복 지출의 「이번 달 생성 여부」, cron 실행 시각(UTC 01:00 = KST 10:00)이 사용자가 보는 날짜와 어긋났다(2026-10-01 점검).
  사용자는 모두 한국에 있다.
- **대안 기각**:
  - JVM 기본 시간대를 Asia/Seoul 로 바꾸기: `createdAt` 같은 감사 시각과 `LocalDateTime.now()` 로 채우는 값이 배포 시점부터 9시간 다른 기준으로 저장된다. 이미 저장된 값과 섞여 정렬과 비교가 틀어진다.
  - 기본 Clock 빈의 시간대를 Asia/Seoul로 바꾸기: API 토큰의 마지막 사용 시각과 폐기 시각도 이 빈을 사용하므로 감사 시각의 저장 기준까지 바뀐다.
  - 사용자 프로필의 timezone 으로 집계마다 경계를 정하기: 모든 집계 쿼리와 스케줄러를 고쳐야 하고, 가족 구성원의 timezone 이 다르면 같은 가족의 「이번 달」 이 사람마다 달라진다.
- **결과**:
  - 얻는 것: 사용자가 보는 날짜와 서버의 날짜 판정이 하루 종일 같다. 반복 지출이 KST 새벽 1시에 생성된다.
  - 감당할 것: 새 코드에서 「오늘」 을 구할 때 `Clock`을 주입받고 업무 시간대를 적용한다. 날짜 없는 지출과 수입도 같은 기준을 쓴다. 감사 시각은 지금처럼 JVM 기본(UTC)이라, 날짜 판정에 감사 시각을 섞어 쓰지 않는다. 프로필 timezone 은 집계에 쓰이지 않는다.
- **적용 범위**: `ClockConfig`, `RecurringExpenseScheduler` 의 `@Scheduled`, 업무 날짜를 정하는 서비스와 컨트롤러. 엔티티 기본값과 응답 `timestamp` 는 해당하지 않는다.
